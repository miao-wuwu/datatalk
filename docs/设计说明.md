# 设计说明

## 1. 问题定义

「自然语言查数据库」的难点不在生成 SQL，而在**生成错了怎么办**。一个只会 `print(sql)` 的 Demo，在真实数据上第一次就会死在：

- 字段名编造（`jobs.job_city` 实际叫 `city`）
- 枚举值编造（`education='实习生'`）
- 口径漂移（问「平均日薪」，它算 `AVG(salary_min)`）
- 多余过滤（问「北京 Python 岗」，它塞一个 `education='不限'`，结果少一半）
- 危险语句（多语句、DDL）

所以本项目的核心资产是**三层校验 + 自修复闭环**，而不是提示词。

## 2. 流程

```
问题
 ├─ （有上下文时）追问改写：「那上海呢」→「上海有多少个岗位」
 ├─ few-shot 检索（关键词重合度，确定性、可解释）
 ├─ Prompt 组装：schema + 指标口径 + 同义词表 + 示例
 ├─ LLM 生成 SQL
 ├─ ① 静态校验：单条、SELECT/WITH、关键字黑名单、表白名单
 ├─ ② 语义校验：表/列存在、枚举值合法、无多余过滤、技能过滤走 job_skills
 ├─ ③ 执行校验：只读连接、8s 超时、200 行上限
 ├─ 失败 → 带着「具体原因」回模型修复（≤2 次）
 ├─ 图表推断（列类型 + 基数 → KPI / 饼 / 柱 / 线）
 └─ 结论生成（规则模板，避免二次调模型带来的延迟与幻觉）
```

每步都写进 `steps`，前端原样展示。这是这个项目最重要的「可解释性」设计：用户能看到它为什么给出这个结果，也能看到它改过什么。

## 3. 关键取舍

**为什么语义校验不交给模型自己反思？**
3B 模型反思时倾向于「再生成一个看起来更像样的」而不是「承认上一个错了」。把校验写成确定性代码，错误信息是精确的（"education 只能取 [...]，不能是 '实习生'"），修复命中率明显更高。

**为什么 few-shot 用关键词检索而不是向量检索？**
示例只有十几条，向量检索带来的收益远小于它的不确定性（embedding 模型 274MB、冷启动慢）。关键词重合度可解释、零依赖，且能随示例增长平稳退化。

**为什么结论用模板而不再调一次模型？**
延迟从 2~3s 降到 0ms，且数字绝不会说错。代价是措辞生硬——这是有意识的取舍，`docs/eval-report.md` 里会对比两种做法。

**为什么只读连接 + 超时 + 限行三层一起上？**
任何一层单独都可能被绕过：只读挡不住写（`WITH ... INSERT`），超时挡不住大结果集（一次扫全表返回 100 万行），限行挡不住笛卡尔积。组合起来才成立。

## 4. 模型与质量

| 模型 | 体验 | 说明 |
| --- | --- | --- |
| Qwen2.5-3B（本机，默认） | 简单问题一次过；多表聚合常需 1~2 次修复 | 8GB 显存可跑，完全离线 |
| 7B 级 coder 模型 | 一次成功率明显提升 | 建议有 8GB+ 显存时切换 |
| 云端大模型（DeepSeek 等） | 基本一次过 | 改 `LLM_BASE_URL/LLM_MODEL/LLM_API_KEY` 即可 |

模型只是可替换件：护栏和评测不依赖具体模型。

## 5. 评测：结果

已经跑完，不是计划。

- **数据集**：102 题（计数 20 / 薪资 21 / 分组 20 / 技能 20 / 组合 21），每题带金标准 SQL 与**金标准结果集**
- **判定**：比较执行结果集（行序无关、浮点容差 0.05），不比 SQL 字符串——同一语义有多种写法
- **指标**：执行准确率 82.4%（84/102）、首次生成 66.7%、自修复救回 16 题、平均 838ms / P95 2.0s
- **对照（ablation）**：关掉语义校验后 74.5%，且自修复只救回 3 题 → **语义校验净 +7.8pt**，收益几乎全部来自「修复能否修对」

结论：在 3B 这个量级上，**反馈质量比生成能力更决定成败**。同一模型，SQLite 原生报错（`no such column`）几乎无法指导修复，而语义校验给出的（`education 只能取 [...]`）能。

跑法：

```powershell
cd backend
..\.venv\Scripts\python.exe -m scripts.eval_nl2sql            # 写 docs/eval-report.md
$env:SEMANTIC_CHECK="0"; ..\.venv\Scripts\python.exe -m scripts.eval_nl2sql --tag no-lint
```

## 6. 多轮追问：为什么先改写、再生成

追问有三种做法：

| 做法 | 问题 |
| --- | --- |
| 把历史拼进 prompt，直接生成 SQL | 理解错了只能靠读 SQL 猜，错了也难定位 |
| 前端自己记住上次的过滤条件 | 逻辑跑到前端，服务端无法复用；换个客户端就没了 |
| **先把追问改写成独立问题**（采用） | 多一次调用（~0.5s），换来一个**人话的、可审计的中间态** |

改写放在 `pipeline._rewrite()`，失败或超时静默退回原问题（`理解追问` 步骤标 `skipped`），不阻断主流程。改写结果会作为「已理解为：…」显示在结果卡上，用户一眼就能发现「它把深圳理解成上海了」。

改写后的 `standalone` 会一路传到生成、语义校验、自修复——避免出现「用改写后的问题生成 SQL，却用原问题做语义校验」这种半吊子状态。

## 7. 接生产库：账号 + 白名单

四层，任意一层都能单独兜住：

1. **只读连接**：SQLite 用 `file:...?mode=ro` + `PRAGMA query_only`；换 PG/MySQL 就建只读账号
2. **只读视图**：把 `jobs`/`companies` 包成 `jobs_v`，账号对原表无权限
3. **表白名单**：`ALLOWED_TABLES=jobs_v,companies_v`，同时作用于 schema 暴露、静态校验、语义校验三处
4. **单条 SELECT + 8s 超时 + 200 行上限**

白名单的实现要注意 CTE：`WITH top AS (...) SELECT * FROM top` 里的 `top` 不是表，静态校验会先把 CTE 名排除掉再比对白名单，否则正常查询会被误杀（`backend/tests/test_guards.py::test_cte_name_is_not_a_table`）。

## 8. 已知限制

- 3B 模型在「分组 + 多条件 + 中位数」这类组合题上仍会写错，靠自修复兜底；102 题里失败的 20 题中约一半是口径歧义（「最高日薪」用 max 还是 avg）
- 追问改写依赖提示词，短句歧义时可能改写过度，前端把改写结果展示出来让用户核对
- Docker 镜像未在本机实测（无 Docker 环境），文件按官方镜像写
- 评测是单轮的：多轮追问目前只有人工冒烟，没有并入 102 题自动评测
