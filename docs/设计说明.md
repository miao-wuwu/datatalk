# 设计说明

## 1. 问题定义

「自然语言查数据库」的难点不在生成 SQL，而在**生成错了怎么办**。一个只会 `print(sql)` 的 Demo，在真实数据上第一次就会死在：

- 字段名编造（`jobs.job_city` 实际叫 `city`）
- 枚举值编造（`education='实习生'`）
- 口径漂移（问「平均日薪」，它算 `AVG(salary_min)`）
- 多余过滤（问「北京 Python 岗」，它塞一个 `education='不限'`，结果少一半）
- 危险语句（多语句、DDL）

所以本项目的核心资产是**三层校验 + 自修复闭环**，而不是提示词。

## 2. 流程

```
问题
 ├─ few-shot 检索（关键词重合度，确定性、可解释）
 ├─ Prompt 组装：schema + 指标口径 + 同义词表 + 示例
 ├─ LLM 生成 SQL
 ├─ ① 静态校验：单条、SELECT/WITH、关键字黑名单
 ├─ ② 语义校验：表/列存在、枚举值合法、无多余过滤、技能过滤走 job_skills
 ├─ ③ 执行校验：只读连接、8s 超时、200 行上限
 ├─ 失败 → 带着「具体原因」回模型修复（≤2 次）
 ├─ 图表推断（列类型 + 基数 → KPI / 饼 / 柱 / 线）
 └─ 结论生成（规则模板，避免二次调模型带来的延迟与幻觉）
```

每步都写进 `steps`，前端原样展示。这是这个项目最重要的「可解释性」设计：用户能看到它为什么给出这个结果，也能看到它改过什么。

## 3. 关键取舍

**为什么语义校验不交给模型自己反思？**
3B 模型反思时倾向于「再生成一个看起来更像样的」而不是「承认上一个错了」。把校验写成确定性代码，错误信息是精确的（"education 只能取 [...]，不能是 '实习生'"），修复命中率明显更高。

**为什么 few-shot 用关键词检索而不是向量检索？**
示例只有十几条，向量检索带来的收益远小于它的不确定性（embedding 模型 274MB、冷启动慢）。关键词重合度可解释、零依赖，且能随示例增长平稳退化。

**为什么结论用模板而不再调一次模型？**
延迟从 2~3s 降到 0ms，且数字绝不会说错。代价是措辞生硬——这是有意识的取舍，`docs/eval-report.md` 里会对比两种做法。

**为什么只读连接 + 超时 + 限行三层一起上？**
任何一层单独都可能被绕过：只读挡不住写（`WITH ... INSERT`），超时挡不住大结果集（一次扫全表返回 100 万行），限行挡不住笛卡尔积。组合起来才成立。

## 4. 模型与质量

| 模型 | 体验 | 说明 |
| --- | --- | --- |
| Qwen2.5-3B（本机，默认） | 简单问题一次过；多表聚合常需 1~2 次修复 | 8GB 显存可跑，完全离线 |
| 7B 级 coder 模型 | 一次成功率明显提升 | 建议有 8GB+ 显存时切换 |
| 云端大模型（DeepSeek 等） | 基本一次过 | 改 `LLM_BASE_URL/LLM_MODEL/LLM_API_KEY` 即可 |

模型只是可替换件：护栏和评测不依赖具体模型。

## 5. 评测设计（下一步）

- **数据集**：100 个问题 + 金标准 SQL + 金标准结果集（部分题允许结果集等价而非 SQL 文本相同）
- **判定**：比较**执行结果集**（排序无关、浮点容差），而不是比较 SQL 字符串——同一语义有多种写法
- **指标**：执行准确率 EX、首次生成准确率、自修复成功率、平均延迟、平均修复轮次
- **对照**：关闭语义校验 vs 开启，量化「护栏到底值多少」

这套评测可以全自动跑，不需要人工标注分数。
